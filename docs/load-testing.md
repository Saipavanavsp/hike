# Load testing

_Generated by `python loadtest/run.py`. Raw Locust CSVs are in `loadtest/results/`._

**Setup.** Windows 11, Intel64 Family 6 Model 197 Stepping 2, GenuineIntel, 16 logical CPUs, Docker Desktop. Locust and the whole stack (nginx, one FastAPI process, Celery worker with concurrency 2, PostgreSQL, Redis) run on the **same laptop**, so Locust competes with the app for CPU. These numbers describe this machine, not a production deployment; they are useful for finding bottlenecks and comparing changes, not as capacity guarantees. Run on 2026-11-02.

**Traffic.** Each stage ramps to the given number of concurrent users, then measures for the stated time (ramp-up excluded). Users mostly browse: search (30% with location filters, some misspelt queries, some page 2), job pages and autocomplete, half of them signed in so match scores are computed; others check their applications and notifications. Five recruiters load ranked candidate pipelines and five uploaders send real PDF resumes and wait for the background worker to parse them. Every user waits 1-5 s between actions.

## Finding: connection-pool deadlock at 500 users (fixed)

The first run of this test, against the code before the fix, handled 100 and 250 users but collapsed at 500, and the API stayed unresponsive after the test ended (`/health` took 60 s). PostgreSQL showed all 15 pooled connections `idle in transaction` with the CPU idle. FastAPI runs sync endpoints and the cleanup of sync generator dependencies in a 40-thread pool; once all threads were blocked waiting for a connection, the requests holding the connections could not get a thread to finish and return them.

Fix (`app/db/session.py`, `ConcurrencyLimitMiddleware` in `app/core/observability.py`):

- the session dependency is an async generator, so connections are returned on the event loop and never wait for a thread;
- at most `MAX_CONCURRENT_REQUESTS` (15) requests run at once; the rest wait on the event loop, holding nothing, and get `503 Retry-After` after 10 s instead of piling up (health checks and metrics are exempt);
- the pool (15 + 15 overflow) covers two sessions per running request, and its timeout is 10 s.

**Next limit.** At 500 users the single API process runs at about 90% CPU and p95 latency rises from ~30 ms to ~230 ms: the process, not PostgreSQL (about 20% CPU, under 20 connections) or Redis, is the bottleneck. `WEB_CONCURRENCY=N` starts N API processes; each has its own pool of up to 30 connections, so keep N x 30 plus the worker's connections below PostgreSQL's `max_connections` (100).
